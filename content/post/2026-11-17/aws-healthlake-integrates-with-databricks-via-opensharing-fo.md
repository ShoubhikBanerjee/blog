# AWS HealthLake Integrates with Databricks via OpenSharing for Live Clinical Data Analytics

AWS and Databricks have announced a new integration that connects AWS HealthLake with Databricks through the OpenSharing project, enabling direct querying of clinical data without export pipelines or duplication.

## 🔍 Overview

Many healthcare and life sciences organizations have standardized on AWS HealthLake to manage clinical data, but extending that data to other platforms for analytics and AI has traditionally required more effort. This new solution allows users to query HealthLake data live from Databricks, bringing Databricks governance, analytics, and AI capabilities to clinical datasets.

## 🧩 How it works

The integration uses OpenSharing to securely expose data in HealthLake without requiring any export pipelines or data duplication. A custom OpenSharing server runs as a Databricks App, a fully managed serverless deployment.

On every table request, the server uses Lake Formation credentials, resolves the table's current Iceberg snapshot, pre-signs the data files, and returns them in a standard OpenSharing response. Databricks compute then reads the files directly from S3, so no data passes through the server. AWS trusts the app's own Databricks identity through OIDC federation, protecting sensitive healthcare data.

## ⚙️ Key details

- HealthLake stores its analytics tables as Apache Iceberg tables in an Amazon S3 bucket owned by the HealthLake service
- Customer IAM roles can't read that bucket directly, so external tools such as Unity Catalog have no direct path to the underlying data
- Today, the only way HealthLake provides direct access to its underlying Iceberg tables is through temporary credentials generated by Lake Formation, and Unity Catalog cannot request these credentials itself
- Databricks mounts the share in Unity Catalog like any other share, making the data available for governed analytics, notebooks, dashboards, AI, and natural language exploration with Genie One
- Unity Catalog becomes the entry point for access, with grants, fine-grained access controls (FGAC), attribute-based access controls (ABAC), and role-based access controls (RBAC) on the shared catalog specifying who is permitted to see and query each table
- Access and usage can also be audited like any other data asset in Unity Catalog, making clinical data easier to govern and secure

## 🚀 Availability

Organizations can create and curate Genie Agents over the shared catalog by defining core clinical tables, adding plain-language descriptions, and teaching them how to define and interpret clinical concepts like A1C. A user can then ask a question like "How is average A1C trending by month?" and Genie One understands the context, finds the curated Genie Agent, generates the SQL, and returns the summarized answer with a table and chart, all while respecting Unity Catalog permissions.

## 💡 Why it matters

Organizations no longer need to copy and export data to external analytics tools, or rely solely on Athena or Redshift for analytics. The same clinical data can now be explored through natural language with Genie One, allowing users to surface insights without specialized technical workflows or data duplication.
