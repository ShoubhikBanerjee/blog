# Multi-Node LLM Inference on Amazon EKS with Ray LLM Deep Learning Containers

This post shows how to deploy one large language model (LLM) across two GPU nodes on Amazon Elastic Kubernetes Service (Amazon EKS) using the multi‑node Ray LLM Deep Learning Containers. The deployment separates the prefill and decode phases onto distinct GPU workers behind a single OpenAI‑compatible endpoint.

## 🔍 Overview
- Ray is a distributed compute framework; Ray Serve deployments can span multiple nodes.
- AWS Deep Learning Containers (DLCs) are pre‑built, performance‑optimized Docker images that bundle a framework, its dependencies, and the GPU stack into a tested, patched combination you can pull and use immediately.
- The new Ray LLM DLC extends this approach to multi‑node inference.

## 🏗️ Architecture
- **CPU system node (m7i.xlarge)** runs system workloads, the KubeRay operator, and the Ray head pod (CPU‑only).
- **Two GPU worker nodes (g6.8xlarge)** run Ray workers: one dedicated to the *prefill* phase, the other to the *decode* phase.
- Both GPU nodes pull the Ray LLM DLC from Amazon Elastic Container Registry (Amazon ECR).
- KubeRay watches the RayService you apply and automatically wires the head‑to‑worker join.
- Ray Serve places the prefill and decode deployments on the two GPU workers.
- KV‑cache generated by prefill is transferred to the decode worker over NIXL, using the Elastic Fabric Adapter (EFA) through NIXL’s libfabric backend.

## ⚙️ How It Works
- **Prefill phase**
  - Processes the entire input prompt in parallel.
  - Builds the key‑value (KV) cache.
  - Compute‑bound.
- **Decode phase**
  - Generates the response one token at a time, reading and extending the KV cache.
  - Memory‑bandwidth‑bound.
- Separating the phases prevents compute‑heavy long prompts from stalling token generation for requests already in progress.
- Disaggregation allows each phase to use hardware and serving properties tuned to its workload, improving overall performance at scale.
- The trade‑off is that the KV cache must be handed from prefill to decode quickly enough to retain the benefit.

## 📦 Key Components
| Component | Role |
|---|---|
| Ray LLM DLC | Packages Ray Serve LLM, NVIDIA Inference Transfer Library (NIXL), and the Elastic Fabric Adapter (EFA) stack; exposes an OpenAI‑compatible API with no application code |
| vLLM | Inference engine |
| Ray Serve HTTP | Serving layer |
| NIXL | KV‑cache transfer between nodes |
| EFA stack (libfabric, aws‑ofi‑nccl) | High‑bandwidth node‑to‑node communication |
| AWS Deep Learning Containers | Pre‑built, performance‑optimized Docker images ensuring no version drift between CUDA runtime, framework, and serving layer |

## 🚀 Deployment Details
- The Ray LLM DLC ships Ray Serve LLM, NIXL, and the EFA stack, ready for multi‑node inference.
- No application code is required to expose the OpenAI‑compatible endpoint.
- This multi‑node setup is common for tensor, pipeline, and data parallelism, as well as for prefill/decode disaggregation inference workloads.
- In a previous post, the Ray Serve DLC was used to stand up a small model behind an HTTP endpoint on a single GPU node.

## 💡 Why It Matters
- By assigning prefill and decode to separate GPUs, compute‑heavy prefill work no longer contends with latency‑sensitive decode work.
- Independent scaling of each phase enables better resource utilization and lower latency for LLM serving at scale.
- All components are validated together before each release, guaranteeing compatibility across the CUDA runtime, framework, and serving layer.
